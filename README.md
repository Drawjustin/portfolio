## 핵심 성과

| 성과 | 내용 | 구분 |
|---|---|---|
| **1,500ms → 50ms** | 요청이 몰릴 때 응답 시간, gap lock 원인 제거 | 실무 |
| **약 60만 건** | 6개월간 포인트 증감, 잔액·이력 대조 불일치 0건 | 실무 |

## 일하는 방식

- **원인은 데이터로 좁힙니다.** 재현되지 않던 지연을 슬로우 쿼리와 접속량 대조로 좁혀 gap lock을 찾았습니다.
- **틀려도 되짚을 수 있게 남깁니다.** 포인트의 모든 증감을 두 함수와 이력으로 모아, 실패하면 복원되게 했습니다.
- **동작한 뒤에도 다시 잽니다.** 기능 테스트를 통과한 게이트웨이를 다시 측정해 ReDoS 취약점을 찾았습니다.

## 툰스퀘어 · 백엔드 개발자, 정규직 (2025.04 – 2026.04)

AI 웹툰 창작 서비스(투닝플러스)와 글로벌 콘텐츠 판매 서비스(Deev)의 서버 API와 관리자 기능을 개발·운영했습니다. 월 이용자 약 3천 명 규모입니다. `Node.js` `TypeScript` `MySQL`

**재현되지 않던 지연의 원인 진단** (단독 수행)
- 문제: 요청이 몰릴 때만 지연·오류가 발생하고, 쿼리를 단독 실행하면 정상
- 원인: 인덱스 없는 조건의 DELETE가 gap lock을 넓게 걸어 요청끼리 서로 대기
- 결과: 인덱스 추가로 요청이 몰릴 때 응답 **1,500ms → 50ms**, 락 대기 오류 일 평균 **5건 → 0건**

**포인트 정합성 설계와 복구 경로** (사수와 2인 설계)
- 여러 경로에서 바뀌던 잔액을 적립·차감 두 함수로 모으고 사유·담당자를 이력으로 기록
- 외부 AI 호출 실패 시 차감 내역대로 복원, 복원도 실패하면 알림 발송, 동시 요청은 잠금으로 이중 차감 방지
- 결과: 6개월간 **약 60만 건** 처리, 이력 합계와 잔액을 주기적으로 쿼리로 대조해 **불일치 0건**

**QA 지원 도구로 확인 대기 제거** (먼저 제안)
- 문제: QA 담당자 한 명이 두 서비스를 맡으며 재가입 제한(30일), 포인트 만료(배치)처럼 시간이 지나야 확인되는 항목이 밀림
- 해결: 날짜 수정과 계정 탈퇴를 관리자 기능으로 만들고, 만료일 수정은 실서비스 배치와 같은 단계를 거치게 함. 운영 환경에서는 차단
- 결과: 가장 오래 기다려야 했던 확인 **30일 → 즉시**

> 사내 코드와 화면 없이 구조만 다시 정리했습니다.

## KAIROS · 기업용 AI 게이트웨이 (개인 프로젝트, 2026.04 – 2026.09)

사내에서 AI를 쓰되 기밀이 외부로 나가지 않게 하는 게이트웨이입니다. OpenAI·Claude·Gemini 호출의 권한, 민감정보, 예산을 한 곳에서 통제합니다. `Kotlin` `Spring Boot 3.5` `Terraform` `AWS` · 커밋 95건, 테스트 137건 · [저장소](https://github.com/Drawjustin/KAIROS)

```
업무망 (공인 IP·기본 경로 없음) → KAIROS (인증·민감정보·예산·원장) → NAT + Squid (허용 provider만) → 외부 AI
```

- **구조로 막은 외부 경로**: 라우팅 테이블에 외부 경로 자체를 두지 않아, 업무망 발신 119건 전부 VPC 내부, 외부 0건·REJECT 0건
- **보내기 전에 처리하는 민감정보**: 주민·카드번호는 차단(provider 미호출), 전화·이메일은 마스킹 후 전송
- **개발 AI도 같은 관문**: Claude Code·Codex는 직접 구현한 MCP endpoint를 거쳐 허용된 자료만 받고, 모델이 고른 도구는 실행 직전에 다시 검증

**기능 테스트를 통과한 뒤에도 다시 측정했습니다**

| 상황 | 결과 | 내용 |
|---|---|---|
| 입력이 길어질 때 | **167.8초 → 114ms** | 요청 1건(상한 20,000자 메시지 50개) 기준. 허용된 메시지 1건만으로도 3.3초 걸리던 이메일 정규식의 ReDoS를 수정(2ms)하고 회귀 테스트로 고정 |
| 요청이 동시에 겹칠 때 | **정확히 100건** | 한도 100, 동시 300건에서 조건부 UPDATE로 정확히 통제. 조회 후 갱신 방식은 300건이 모두 통과했는데 사용량은 1건만 기록됨(lost update) |
| 부하가 걸리고 외부가 멈출 때 | **오버헤드 약 30ms** | 200 VUs에서 성공 응답 p95 3.03초, mock 지연 3초를 뺀 게이트웨이 몫. provider별 동시 호출 32건을 넘는 요청은 즉시 거절해 처리 중인 요청을 지키고, OpenAI 장애 시 서킷을 열어 허용된 모델 안에서만 Claude로 전환 |

## 공무원 S.O.S · 행정 업무 AI (KT AIVLE SCHOOL 빅프로젝트, 2025.01 – 2025.02)

현직 공무원 인터뷰로 확인한 전화 응대 부담을 줄이는 민원 처리 시스템입니다. 6인 팀, 49일 중 저는 모델 학습을 제외한 통화 파트의 백엔드·인프라를 맡았습니다. [저장소](https://github.com/Drawjustin/KT_BIG_PROJECT)

```
민원인 전화 → Twilio(SIP 트렁크 → 웹훅) → Google STT → 분류 서버(BERT, 팀원 담당) → 분류 결과 음성 확인 → 담당 부서 연결
```

- **통신사 제약은 목적을 바꿔 풀었습니다**: 국내 통신사의 최소 회선 요건에 막히자, 필요한 것은 통신사 계약이 아니라 음성을 받아오는 경로라고 보고 회선을 SaaS로 제공하는 Twilio로 구현
- **STT는 목적에 맞는 수준으로**: 클로바·구글·Twilio를 같은 음성으로 비교하고, 분류의 입력이라 정확도 대비 단가를 기준으로 선택
- **AI가 틀릴 때 바로잡을 지점**: 분류 결과를 음성으로 확인받고, 분류 서버가 응답하지 않아도 기본값으로 통화 유지 (팀에 제안해 채택, 직접 구현)
- 최종 시연: 전화 한 통으로 접수부터 답변 초안까지 동작, 분류 서버를 중단해도 통화 유지
